# verifier-skeptic

## 1. What this skill is

An adversarial verifier for shipped features. When you invoke it against a Jira Epic that someone
called "done", it assumes the delivery has mistakes and its whole job is to find as many as possible
before the Epic is archived. It runs three lanes — architecture, functionality, and pixel-perfect
design — and produces three durable outputs: a numbered findings list, one Jira Task per finding
(labeled `verifier`), and an HTML dashboard report generated by the `agentic-report-creator` skill.

**This skill NEVER edits application code.** Not to fix a typo it noticed in passing, not for a
one-line CSS tweak, not for anything. Its only outputs are findings, tickets, and a report. A
separate fix agent — a different invocation, a different worker — picks up the tickets later by
filtering on the `verifier` label. If you catch yourself opening a source file to change it, stop:
that is out of scope by definition.

## 2. When to invoke

Invoke when ALL of these hold:

1. A design source of truth exists (a prototype directory, a Figma link, or a PRD naming success
   criteria) AND shipped code exists. This skill needs BOTH — it compares one against the other.
2. The user asks for one of: "pixel-perfect audit", "verification", "проверка после реализации",
   "аудит эпика", "проверить что сделано соответствует дизайну", "найти расхождения с прототипом",
   "skeptical review", "audit this epic before we close it".
3. A Jira Epic is being closed or archived and the owner wants a durable audit trail.
4. The user says "они допустили ошибки, я вижу" / "I can see they made mistakes" or similar — take
   that as ground truth and hunt.

Do NOT invoke:

1. Before implementation is complete — there is nothing to audit yet.
2. For pure API/backend work with no user-facing surface — the pixel-perfect lane is meaningless
   there (run only the architecture and functionality lanes, or decline).
3. When the user actually wants fixes applied — this skill only finds. Point them at a fix agent
   filtering on the `verifier` label after the audit lands.
4. When there is no design source of truth to compare against — without a reference, "deviation" has
   no meaning. Escalate to the invoker to supply one.
5. **When the real ask is "did the fixes from the last audit stick?"** — that is a REGRESSION CHECK,
   not an audit. It is defined by prior findings, and this skill is forbidden from reading them
   (section 6). Run it as a separate lane with a separate worker whose explicit job is to walk the
   prior tickets. Never bundle it into a fresh audit: the moment one worker does both, the fresh
   audit is anchored and its independence is gone. A fresh audit re-finds any unfixed deviation on
   its own merits anyway — that IS the regression signal, produced honestly.

## 3. Contract

### Inputs (gather these from the invoker before starting)

1. **Jira Epic key** — e.g. `TLM-360`. Every finding files under this Epic.
2. **Design source of truth** — one or more of:
   - A directory of prototype files (e.g. `reference/prototype_v3/`).
   - A Figma link (you will need a browser/MCP to render frames).
   - A PRD document naming success criteria and PRD "traps" (known-hard requirements to verify).
3. **Component mapping** (optional) — which prototype file maps to which shipped surface. If the
   invoker has one, use it. If not, discover it from routes + file names and record what you inferred.
4. **Severity threshold** (optional) — default is to report CRITICAL / MAJOR / MINOR and suppress
   trivial polish only if the owner explicitly asks. Over-reporting is the default posture (see
   section 6).
5. **Custom labels** (optional) — any extra Jira labels the invoker wants on every ticket (e.g.
   `phase-24`, `wave-2`).
6. **Prior-audit context** — **NONE, and never request it.** Do not ask the invoker for the last
   report, the previous findings, or "what was already fixed", and refuse it if offered (section 6).
   The inputs above are the complete list; anything beyond them is another agent's conclusions.

### The brief template (what an invoker/orchestrator hands a verifier worker)

Copy this shape when spawning a verifier. It is deliberately a *scope + boundary* brief, not a
findings hand-down — the reading boundary is part of the contract, not an afterthought:

```md
## Mission — independent audit of <EPIC-KEY>

Invoke the `verifier-skeptic` skill. READ-ONLY: find and report, never edit app code.

**Audit target:** <EPIC-KEY> — <one line of scope> at commit <SHA> (<prod|branch>).
**Design source:** <path/to/prototype | Figma link | PRD path>
**Component mapping:** <path/to/mapping.md, or "none — discover from routes and record what you inferred">
**Custom labels:** <phase-NN>, <component-slug>, …
**Report to:** docs/reports/<...>/index.html  (EN + ru/, via `agentic-report-creator`)

### Independence — HARD RULE
You are a FRESH pair of eyes. Read ONLY the shipped code + the design source above.
DO NOT read: prior verification reports (`docs/reports/verifications/**`, ANY run),
any prior payload.json, prior findings tickets (`labels = verifier`) or their comments,
the delivery agent's PR description / handoff notes, or prior audit screenshots.
If any prior context reaches you, decline it, name it in your report, and proceed from
code + design only. Regression-checking prior fixes is a DIFFERENT worker — not you.

### Deliverables
Numbered findings (integers, never letters) · one Jira Task per finding labeled `verifier`
· HTML dashboard report · ONE compact SendMessage back (path, counts by severity, top keys).
```

An invoker who cannot write that brief without pasting last run's findings into it wants a
regression check, not an audit — see section 2.

### Outputs (all three are mandatory)

1. **Numbered findings list**, canonical structure — numbers only, never letters, each naming its
   Jira ticket first:
   ```
   1. TLM-432 — Stage-nav shell absent from Suppliers layout — CRITICAL — functionality
   2. TLM-433 — Plan header uses pill instead of prototype's rectangular tab — MAJOR — design
   3. TLM-434 — Empty state copy missing on the suppliers grid — MINOR — functionality
   ```
2. **One Jira Task per finding**, filed under the Epic, labeled `verifier` (mandatory) plus the kind
   label(s). See section 7.
3. **HTML dashboard report** produced by `agentic-report-creator` from the findings JSON you prepare.
   See section 8. Do NOT hand-roll HTML, and do NOT write the report to `docs/reviews/*.md` — that
   path is gitignored in most of this team's projects (see section 10).

Then send ONE compact report to the invoker: report path, count of findings by severity, and the top
Jira keys. Keep it small — the invoker relays it, it does not need the finding bodies.

## 4. The three verification lanes

Run all three lanes. Cross-link findings that span more than one (a missing component is both an
architecture gap and a design gap — file it once, name both lanes, apply both labels). Every finding
names exactly one PRIMARY lane in its number line; secondary lanes go in the labels.

### Lane 1 — Architecture

Read the design source and the shipped code as *systems* and compare structure. Ask:

1. Are the modules named and organized the way the design implied?
2. Is separation of concerns respected — server-only code stays server-side, design-system (DS)
   primitives are reused rather than re-implemented per feature?
3. Are the state boundaries the design demanded actually in place (context / props / URL / DB)?
4. Is there a component the design mandated that never got created? Or one that exists but the design
   never asked for?
5. Are there correctness landmines — a migration that overwrites data, a query with no tenant scoping,
   an auth check that runs client-side only?

Per finding, deliver: an architecture description, the prototype reference (file:line or frame), the
shipped reference (file:line), and why it matters (impact on maintainability, correctness,
testability). A small mermaid diagram embedded in the report often makes the gap obvious — include one
when structure is the point.

### Lane 2 — Functionality

Drive the shipped app. For every user-facing flow the design promised, exercise it end-to-end and
record whether it works.

1. Run the app in a fresh checkout (section 9).
2. Use the `playwright-cli` skill to drive flows led by the design source (section 5 has the command
   reference; the same browser session works for functional and visual passes).
3. For every route/flow: attempt the happy path AND at least one edge — empty state, invalid input,
   offline/error. Record the OBSERVED behaviour, not the intended one.
4. Classify severity honestly:
   - **CRITICAL** — the flow crashes, inputs are accepted silently with no feedback, a promised path
     is unreachable from the UI, or data is lost/corrupted.
   - **MAJOR** — the flow works but diverges materially from the design's promise (wrong destination,
     missing confirmation, broken back-navigation).
   - **MINOR** — cosmetic or copy-level gaps that do not block the flow.

Per finding, deliver: reproduction steps, expected behaviour (per design), actual behaviour, a
screenshot of the failure state, and severity. A functional finding without a repro is not actionable.

### Lane 3 — Design (pixel-perfect)

For each surface, compare the shipped rendering against the design at pixel level. Not "does it look
similar" — literal geometry, typography, colour, radius, state, motion. The method is the visual diff
loop in section 5; the lenses below are what you look for once you have the two images side by side.

Nine lenses per surface (skip a lens only if it genuinely does not apply):

1. **Component fidelity** — is the correct DS component actually used, or a look-alike re-implementation?
2. **Layout and structure** — columns, sections, grid, order of regions.
3. **Spacing and density** — paddings, gaps, gutters, line-height rhythm.
4. **Typography** — size, weight, tracking, CAPS vs Title Case, font family, line-height.
5. **Colour and tokens** — fills, borders, state colours; measured, not eyeballed.
6. **Radius, elevation, shadows.**
7. **State affordances** — hover, focus, active, disabled, empty, loading, error. These are where
   regressions hide because the happy-path screenshot never shows them.
8. **Motion** — transitions, easing, duration.
9. **Dark-theme parity** — re-run every lens in dark mode. Dark is the single most common place a
   shipped surface silently diverges.

For print surfaces, add a print pass: `emulateMedia({ media: 'print' })` and screenshot each paper
size × orientation the design specifies.

Per finding, deliver: the lens, the measured delta (e.g. "spacing 24px shipped vs 16px prototype",
"radius 12px vs 8px"), the shipped screenshot, the prototype screenshot, and the diff artifact if you
produced one. A visual finding without screenshots is a half-finding (section 10).

## 5. Pixel-perfect visual loop

Use the `playwright-cli` skill. The loop is: screenshot the shipped surface at a controlled viewport →
screenshot (or render) the design counterpart at the SAME viewport → compare → any delta above a small
threshold is a finding. Screenshot in BOTH light and dark every time.

**The playwright-cli commands you will use** (real API — verify against the `playwright-cli` skill):

```bash
# Named session so shipped and prototype tabs stay separate. Open once.
playwright-cli -s=audit open --browser=chromium

# Shipped surface, controlled viewport, save a named screenshot.
playwright-cli -s=audit goto "http://localhost:3000/suppliers/plan"
playwright-cli -s=audit resize 1440 900
playwright-cli -s=audit screenshot --filename=.artifacts/audit/plan-shipped-light.png

# Toggle dark, let the transition settle, re-screenshot.
# (Use the project's real dark-mode switch — dataset.theme, a class on <html>, or a localStorage key.)
playwright-cli -s=audit eval "document.documentElement.dataset.theme = 'dark'"
playwright-cli -s=audit screenshot --filename=.artifacts/audit/plan-shipped-dark.png

# Full-page (not just viewport) capture goes through run-code:
playwright-cli -s=audit run-code "async page => await page.screenshot({ path: '.artifacts/audit/plan-shipped-full.png', fullPage: true })"

# Print media, per paper size:
playwright-cli -s=audit run-code "async page => { await page.emulateMedia({ media: 'print' }); await page.screenshot({ path: '.artifacts/audit/menu-print-a4.png', fullPage: true }); }"
```

**The design counterpart:**

1. If the design source is a live prototype HTML (e.g. a standalone build in `reference/prototype_v3/`),
   open it via `file://` in the same viewport and screenshot it the same way:
   ```bash
   playwright-cli -s=proto open --browser=chromium
   playwright-cli -s=proto goto "file:///abs/path/reference/prototype_v3/suppliers-plan.html"
   playwright-cli -s=proto resize 1440 900
   playwright-cli -s=proto screenshot --filename=.artifacts/audit/plan-prototype-light.png
   ```
2. If the design source is Figma, render the frame via the browser/MCP and export it at the matching
   viewport.
3. If neither renders (JSX-only prototype, no build), read the prototype CSS + JSX line by line and
   encode the intended layout as a precise text description, then compare the shipped screenshot
   against that description. This is the weakest evidence — say so in the finding.

**Producing the diff — pick per audit and DOCUMENT which technique produced each finding:**

1. **`pixelmatch` in a small ad-hoc Node script — the DEFAULT for one-shot audits.** It needs no
   committed baselines, runs in seconds, and emits a per-region diff PNG you attach to the report as
   evidence. Both inputs must be the SAME dimensions (identical viewport + full-page flag), or
   `pixelmatch` throws. The runnable harness is in `references/pixel-perfect-loop.md`; the core call:
   ```js
   const diffCount = pixelmatch(shipped.data, proto.data, diff.data, width, height, { threshold: 0.1 });
   // threshold 0.1 = fairly strict per-pixel YIQ tolerance; diffCount is the number of differing pixels.
   ```
2. **Playwright's built-in `toHaveScreenshot()`** — the right tool for CI regression, the WRONG tool
   for a one-shot audit: it requires committed `.png` baselines and a test harness you would have to
   bootstrap. Use it only if the project already has visual baselines wired.
3. **Manual side-by-side inspection** — cheapest, always available, slowest to be exhaustive. Fine for
   a handful of surfaces; document that the finding came from manual inspection so a reviewer can redo it.

**Thresholds (adversarial, not lenient):** colour deltas above ~2% in perceptual space, spacing deltas
above ~4px, any radius/weight/family mismatch, any missing state — all findings. `pixelmatch` diff
counts are a triage signal, not a verdict: a high count tells you WHERE to look, then you name the
specific lens and measured delta by hand.

## 6. Adversarial stance — the mindset

The skill is called *skeptic* for a reason. Independence comes first: a verifier that has read the
last audit is no longer verifying, it is grading the fixes.

### Independence — HARD RULE

> **A fresh audit reads ONLY the shipped code and the design source. Never a prior verification
> report, a prior `payload.json`, or prior findings tickets.** Those are another agent's conclusions;
> reading them replaces your eyes with theirs. You would re-find what they found, skip what they
> missed, and inherit every mistake they made — while reporting it as independent confirmation.
> **Checking whether prior fixes stuck is a REGRESSION CHECK: a separate lane, a separate worker,
> a separate run. Never bundled into a fresh audit.**

The reading boundary, concretely:

| ✅ READ — the two sides you compare        | ❌ DO NOT READ — someone else's conclusions            |
|-------------------------------------------|--------------------------------------------------------|
| Shipped code at the audited commit         | Any prior verification report (`docs/reports/verifications/**`, any run) |
| The running shipped app                    | Any prior `payload.json` / findings JSON               |
| The design source (prototype / Figma / PRD)| Prior findings tickets (`labels = verifier`) and their comments |
| The component mapping the invoker supplied | The delivery agent's PR description, self-review, or handoff notes |
| Design tokens / CSS the prototype ships    | A prior audit's screenshots or diff artifacts          |
| Code comments + ADRs **in the shipped code** (the documented-deviation default below needs them) | Chat/Jira claims that something was "already fixed" or "known" |

Why each denial matters:

1. **Anchoring is not resistible by intent.** "I'll read the old report but stay objective" does not
   work — you cannot un-see a numbered list. Once you know finding 7 was "spacing 24 vs 16", you
   check that spacing and your attention budget for everything else quietly shrinks. The only
   defense is not reading it.
2. **A prior audit's blind spots become yours.** If the last verifier never opened dark mode, and you
   take its list as the map, dark mode stays unaudited forever — across every run. Fresh eyes exist
   precisely to find what the map lacks.
3. **Confirmation stops being evidence.** Two audits that agree are strong signal ONLY if the second
   never saw the first. Otherwise the agreement is an echo, and the owner is told "independently
   confirmed" about a copy.
4. **"Already known" is not a reason to skip.** A deviation that still ships is still a finding, no
   matter how many prior tickets mention it. File it on what you observe today.

If you find yourself opening a prior report "just for context", stop: you have left the skill. If the
invoker hands you one unprompted, **decline it in your report** — name the file you refused and
proceed from code + design only. Independence you silently gave up is worse than the audit you did
not run.

**The one carve-out is filing-time deduplication, and only after the fact.** When a crashed run is
retried, `references/jira-recipes.md` section 7 searches Jira for an existing ticket — that search
runs at FILING time, after the finding is fully formed and written down, purely so a retry updates a
ticket instead of creating a twin. It never runs before or during the hunt, and its result never
edits a finding's content or severity. Look up a ticket only once your own conclusion is already on
paper.

### The defaults

1. **Assume mistakes exist.** Do not attempt to explain them away. The delivery agent already had its
   turn to get it right; your job is to find where it did not.
2. **Undocumented deviation is a finding, full stop.** If a shipped surface differs from the prototype
   and there is no *self-documented reason* in the code (a docstring, an ADR reference, a manifest
   entry), file it. The burden of proof is on the delivery, not on you.
3. **Documented deviation is a push-back to accept.** If the code says `// intentional DS harmonization:
   pill replaces prototype's rectangular tab` or cites an ADR, record it in the report as
   `intentional (documented)` and do NOT file a fix ticket. Documentation is the ONLY thing that
   converts a deviation into a non-finding.
4. **"Close enough" is not a verdict for visuals.** Measure. A 2px gap is a finding if the design said
   0.
5. **Over-report, never under-report.** The fix agent triages and can dismiss trivia later. A finding
   you failed to raise never gets discussed. When you are unsure whether something is a finding, file
   it as MINOR and let triage decide.
6. **Verify your own findings before filing** — but verify to CONFIRM the deviation is real (right
   file, right line, reproduces), not to talk yourself out of it. A finding that turns out to match the
   design on re-check gets dropped; a finding you are merely uncomfortable raising gets filed.

## 7. Jira integration — file each finding as a labeled Task

Every finding becomes a Jira Task under the Epic. This is the mandatory contract with follow-up fix
agents. Obey the `using-jira` skill for all mechanics (Epic+Task hierarchy, assignee = reporter,
tagged summaries, `ATLASSIAN_API_TOKEN` for attachments). Full payloads and the curl attachment recipe
are in `references/jira-recipes.md`; the essentials:

**Ticket shape (`mcp__atlassian__createJiraIssue`):**

1. `issueTypeName: "Task"`
2. `parentKey: "<EPIC-KEY>"` — files the Task under the audited Epic.
3. `assignee` — the Epic's assignee (usually the owner); resolve once via `lookupJiraAccountId`.
4. `summary` — start with area/kind tags in square brackets, then a plain description:
   `[Suppliers][Plan] Stage-nav shell absent from layout`. Reuse the project's existing tag
   vocabulary. Never the section glyph — write the word out.
5. `description` (markdown) — Context (one paragraph), Design source (file:line or frame link),
   Shipped source (file:line), Steps to reproduce (functional) OR screenshot-pair references (visual),
   Severity + rationale. Do NOT propose a fix (section 10).

**Labels — set via `additional_fields: { labels: [...] }`:**

1. `verifier` — **MANDATORY on every single finding, no exceptions.** This is the label fix agents
   filter on (`labels = verifier` in JQL) to find the audit's output. A ticket without it is invisible
   to the fix pipeline and effectively lost.
2. `pixel-perfect` — when the finding is visual (any of the nine design lenses).
3. `architecture` — when the finding is an architectural gap.
4. `functionality` — when the finding is a broken or missing user flow.
5. Any custom labels the invoker requested.

**Screenshots** attach after the Task exists, via the Jira REST API with `ATLASSIAN_API_TOKEN` from
`.env.local` (the MCP has no attachment tool — this is expected, do not declare BLOCKER). Recipe in
`references/jira-recipes.md`.

**After all findings are filed**, add ONE comment to the Epic linking the HTML report and listing every
finding's Jira key. That gives the Epic itself a durable audit trail a future orchestrator can scan.

## 8. Report generation — delegate to `agentic-report-creator`

Do NOT hand-roll HTML. Assemble a structured findings JSON payload and hand it to the
`agentic-report-creator` skill, which owns theming, screenshot lightboxes, numbering, and the
translation shell. The full schema and a complete example live in `references/findings-schema.md`; the
shape at a glance:

```json
{
  "meta": {
    "title": "Suppliers V4 — pixel-perfect audit",
    "epic": "TLM-360",
    "date": "2026-07-15",
    "auditor": "verifier-skeptic",
    "shipped_at": "6b680ff",
    "design_source": "reference/prototype_v3/"
  },
  "verdict": { "score": 73, "level": "MINOR-POLISH", "counts": { "critical": 2, "major": 11, "minor": 7 } },
  "findings": [
    {
      "number": 1,
      "jira": "TLM-432",
      "severity": "CRITICAL",
      "lane": "functionality",
      "area": "Plan navigation",
      "labels": ["verifier", "functionality"],
      "title": "Stage-nav shell absent from suppliers layout",
      "design_ref": "reference/prototype_v3/suppliers-v4.jsx (Sv4Plan)",
      "shipped_ref": "src/app/(app)/suppliers/plan/page.tsx:55-78",
      "description": "…",
      "technique": "playwright + manual",
      "screenshots": [
        { "caption": "Shipped Plan header — no rail", "src": "assets/plan-shipped-light.png" },
        { "caption": "Prototype Plan header — 01-04 rail visible", "src": "assets/plan-prototype-light.png" }
      ]
    }
  ],
  "architecture_notes": [{ "title": "…", "diagram_mermaid": "…" }]
}
```

**Numbers only — 1, 2, 3.** Never `A/B/C`, `F1/F2`, or any letter-based enumeration anywhere in the
report or the findings list. The Jira key is the semantic identifier; the number is a plain top-to-bottom
ordering index the invoker scans by. The `agentic-report-creator` skill and this skill coordinate on the
JSON shape above — if that skill's schema has drifted, its version is authoritative; align to it and
keep the fields it needs.

## 9. Running the app, the auth wall, and DB seeding

These are the practical friction points that stop an audit dead. Resolutions:

**Launching the app** — the app is usually gated on build-tool quirks and DB migrations:

1. Prefer `pnpm build && pnpm start -p <PORT>` (or the project's documented equivalent).
2. If `pnpm build` (Turbopack) fails because of a `node_modules` symlink pointing out of the worktree,
   fall back to `next build --webpack`.
3. Never run a destructive migration to get the app up (e.g. any `db:migrate` variant that resets a
   role password on a shared DB — it drops the connection pooler). Check the project's known-trap
   registry before running any migration.
4. Never run `next dev` on a Next version with the known `loading.tsx` bug — build and start instead.

**The auth wall** — most product surfaces require login, and a scripted audit cannot click through a
real OAuth prompt:

1. Reuse the project's `e2e/_helpers` and `e2e/_seed` patterns if they exist — they encode
   signup → onboarding → seeding for the exact stack, and they are the supported way to get an
   authenticated, populated session.
2. Seed with those helpers so the surfaces have realistic data (empty grids hide half the design).
3. If no e2e helper exists, escalate to the invoker as a BLOCKER. Asking a live human to log in
   mid-audit is not a substitute for a scripted, repeatable flow — and a hand-waved "I analyzed the
   code instead" is not an audit.

**DB seeding side effects** — always tag seeded rows with the project's e2e marker (e.g.
`@e2e.test` in the email/name) and reap them at the end with the project's `cleanupE2E` helper. An
audit that leaves test rows in a shared DB is a defect it introduced.

## 10. Common pitfalls (from real audits)

1. **`docs/reviews/` is gitignored in most of this team's projects.** Do NOT force-add the report doc
   there. Deliver via the HTML dashboard path AND Jira (tickets + attachments + the Epic comment).
   The report survives as a Jira artifact and a closed-PR branch, never as a committed `docs/reviews/*.md`.
2. **Findings without screenshots are half-findings.** If a lens is visual and you cannot show it, the
   finding lacks the evidence a fix agent needs. Attach the screenshot or drop the finding.
3. **Do NOT propose fixes in the ticket.** Describe the deviation, cite the source of truth, show the
   evidence. The fix agent decides HOW. Over-prescribed tickets ("change line 55 to use flex") get
   ignored or, worse, followed blindly into a wrong fix.
4. **Numbered, not lettered.** `1, 2, 3` everywhere. Letters make the list feel arbitrary and break the
   invoker's top-to-bottom scan.
5. **`verifier` label on every finding — non-negotiable.** Fix agents filter on it. Forget it on one
   ticket and that finding silently never gets fixed.
6. **The auth wall kills scripted audits.** Reuse e2e helpers or escalate — never stand in with
   code-only analysis and call it a functional audit.
7. **Turbopack symlink issues in worktrees** — fall back to `next build --webpack` rather than
   abandoning the run.
8. **Mismatched screenshot dimensions break `pixelmatch`.** Same viewport, same full-page flag, on both
   shipped and prototype captures, or the diff step throws.
9. **You are READ-ONLY.** If you find yourself editing a source file, you have left the skill. Back out
   and file a finding instead.
10. **Reading the last audit "for context" destroys the audit.** It feels efficient and it is the
    single most damaging thing you can do to this skill's output: you inherit the prior verifier's
    blind spots, re-find its list, and hand the owner an echo labeled "independent confirmation".
    There is no safe dose and no amount of intent that neutralizes it — the only defense is not
    opening the file (section 6). Same for a prior `payload.json`, prior `verifier` tickets, and the
    delivery agent's own PR notes.
11. **"It's already a known issue" is not a triage step.** If it ships and deviates, it is a finding
    today, regardless of prior tickets. Judge what you observe, not what someone logged.
